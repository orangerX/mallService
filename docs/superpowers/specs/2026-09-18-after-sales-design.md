# 商城售后功能设计

## 1. 背景与目标

当前商城已具备订单提交、商品 SKU 库存、满减优惠券、商城端订单查询和内管端订单查询，但订单状态只有“待支付”，也没有售后数据模型与处理流程。

本次在现有多模块架构中补齐最小订单履约链路，并实现按订单商品行申请的售后功能：

- 商城端支持模拟支付、取消待支付订单、确认收货。
- 内管端支持发货。
- 售后支持“仅退款”和“退货退款”，不支持换货。
- 用户可申请、查询、撤销售后，并在退货退款获批后填写退货物流。
- 管理员可查询、同意、拒绝售后，并确认收到退货和完成退款。
- 退款只记录业务结果与金额，不对接微信支付或其他第三方支付网关。
- 保持项目既有约束：JDK 11、Spring Boot 2.7.18、MyBatis XML、MySQL 8、Redis、JWT，仅 GET/POST、无后端路径变量、事务显式声明 `rollbackFor = Exception.class`。

## 2. 非目标

- 不实现换货。
- 不实现售后图片或视频凭证上传。
- 不实现第三方支付退款、退款回调或资金对账。
- 不实现自动审核、客服协商、平台仲裁、运费赔付或多包裹退货。
- 不新建 Maven 模块；售后领域归属 `mall-order`。
- 不修改已执行的 Flyway V1-V11，只新增 V12。

## 3. 总体架构

售后作为订单领域中的独立聚合实现：订单负责支付、取消、发货和收货；售后单负责申请、审核、退货和退款。商城端和内管端共享 `mall-order` 中的模型、Mapper 和 Service，但分别声明自己的 Controller，避免共享 HTTP 层。

涉及三个独立 Git 项目：

- `mallService`：数据库迁移、订单/售后领域、商城端接口、内管端接口与后端测试。
- `mallPage`：微信小程序订单履约和售后页面。
- `mallManagePage`：Vue 内管订单发货和售后管理页面。

所有状态变更在数据库事务中完成。服务通过锁定订单、订单商品行或售后单，配合唯一约束与受状态条件约束的更新，防止并发下重复申请、重复退款、重复恢复库存或重复退券。

## 4. 订单履约状态

`mall_order.status` 使用以下状态：

| 值 | 状态 | 允许的下一步 |
| --- | --- | --- |
| 1 | 待支付 | 商城用户支付或取消 |
| 2 | 待发货 | 管理员发货；用户可申请仅退款 |
| 3 | 待收货 | 商城用户确认收货；用户可申请仅退款或退货退款 |
| 4 | 已完成 | 完成后 7 天内可申请仅退款或退货退款 |
| 5 | 已取消 | 终态 |

订单增加 `paid_at`、`shipping_company`、`tracking_no`、`shipped_at`、`completed_at`、`cancelled_at`。模拟支付只记录支付时间，不生成第三方支付流水。

待支付订单取消时，恢复订单中全部 SKU 库存，并将该订单占用的用户优惠券恢复为未使用。重复取消、支付已取消订单、取消已支付订单均返回状态冲突。

管理员只能发货待发货订单。发货必须填写物流公司和运单号。如果订单所有商品数量都已在发货前完成退款，则拒绝发货；存在部分发货前退款时，内管详情明确展示各商品的待履约数量。

商城用户只能确认待收货订单。确认后记录 `completed_at`；完成时间是 7 天售后期限的唯一计算基准。

## 5. 数据模型

### 5.1 订单商品行扩展

`mall_order_item` 增加：

- `payment_amount DECIMAL(12,2)`：该商品行分摊后的实付金额。
- `refunded_quantity INT UNSIGNED DEFAULT 0`：已完成退款的数量。
- `refunded_amount DECIMAL(12,2) DEFAULT 0`：已完成退款的金额。

创建订单时，以商品小计占订单商品总额的比例分摊订单实付金额。除最后一行外均四舍五入保留两位，最后一行使用订单实付金额减去前面各行之和，确保所有商品行 `payment_amount` 之和严格等于订单 `payment_amount`。

V12 为历史订单按同一规则补齐分摊金额；历史订单仍保持待支付状态，不会自动取得售后资格。

### 5.2 售后单

新建 `mall_after_sale`，包含：

- 标识：`id`、唯一 `after_sale_no`。
- 归属：`order_id`、`order_item_id`、`user_id`、`sku_id`。
- 申请：`type`、`status`、`quantity`、`reason_code`、`description`。
- 金额：`refund_amount`。
- 审核：`review_remark`、`reject_reason`、`return_address`。
- 退货物流：`return_shipping_company`、`return_tracking_no`。
- 并发约束：`active_marker`。进行中记录为 `1`，终态记录为 `NULL`；唯一索引 `(order_item_id, active_marker)` 保证同一商品行同时只有一个进行中的售后单。
- 时间：`applied_at`、`reviewed_at`、`return_shipped_at`、`refunded_at`、`cancelled_at`、`created_at`、`updated_at`。

售后类型：

| 值 | 类型 |
| --- | --- |
| 1 | 仅退款 |
| 2 | 退货退款 |

售后状态：

| 值 | 状态 | 说明 |
| --- | --- | --- |
| 1 | 待审核 | 用户已提交，等待管理员处理 |
| 2 | 待用户退货 | 退货退款已同意，等待用户填写物流 |
| 3 | 待商家收货 | 用户已提交退货物流 |
| 4 | 已退款 | 终态 |
| 5 | 已拒绝 | 终态 |
| 6 | 已撤销 | 终态 |

### 5.3 售后操作记录

新建 `mall_after_sale_log`，包含 `after_sale_id`、操作者类型、操作者 ID、操作、变更前状态、变更后状态、备注和创建时间。日志只能插入，不提供更新或删除接口。

操作者类型为用户、管理员或系统；操作至少覆盖申请、撤销、同意、拒绝、提交退货物流、确认收货和退款完成。

## 6. 申请资格与退款计算

### 6.1 申请资格

- 待支付、已取消订单不可申请售后。
- 待发货订单只允许申请仅退款。
- 待收货和已完成订单允许申请仅退款或退货退款。
- 已完成订单在 `completed_at` 后 7 个自然日内可申请，精确到毫秒；超过期限返回冲突。
- 同一商品行同时只能存在一个进行中售后单。
- 可申请数量为购买数量减去以下数量：已退款数量，以及当前进行中售后单占用数量。
- 新申请数量必须大于 0 且不超过可申请数量。

预设原因编码为：

- `QUALITY`：质量问题。
- `DAMAGED`：破损腐坏。
- `MISSING_OR_WRONG`：少件或错件。
- `NOT_AS_DESCRIBED`：与描述不符。
- `OTHER`：其他。

文字说明必填，去除首尾空白后长度为 1-500 个字符。首版不接收凭证图片或视频。

### 6.2 退款金额

用户不能填写退款金额。系统基于订单商品行固定的 `payment_amount` 自动计算：

```text
累计目标退款 = round(商品行实付金额 × (已退款数量 + 本次申请数量) ÷ 购买数量, 2)
本次退款金额 = 累计目标退款 - 商品行已退款金额
```

最终一次覆盖剩余全部数量时，本次金额取商品行实付金额减去已退款金额，确保累计值严格等于商品行实付金额。退款金额还必须受订单剩余可退款金额约束，任何情况下累计退款不能超过订单实付金额。

已付款订单退款后不重新发放优惠券。

### 6.3 库存处理

- 待发货订单的仅退款获批时，商品尚未离库，立即按退款数量恢复 SKU 库存。
- 待收货或已完成订单的仅退款表示用户保留商品，不恢复库存。
- 退货退款只在管理员确认收到退货时恢复 SKU 库存。
- 库存恢复与售后单变为已退款、订单商品行退款计数更新、操作日志写入处于同一事务中。
- `product_sku.sales` 表示净成交数量。现有下单逻辑在扣库存时增加销量，因此待支付订单取消和所有退款完成时都按对应数量减少销量。
- 待支付取消、待发货仅退款和退货退款完成时，同时恢复库存并减少销量；发货后的仅退款不恢复库存，但仍减少销量。
- 销量更新带非负条件与下限保护；状态锁和幂等校验保证每笔取消或退款只扣减一次。

## 7. 售后状态流转

### 7.1 仅退款

```text
待审核 --管理员同意--> 已退款
待审核 --管理员拒绝--> 已拒绝
待审核 --用户撤销--> 已撤销
```

管理员同意后在同一事务中完成退款记账。待发货订单同时恢复相应库存；其他订单状态不恢复库存。

### 7.2 退货退款

```text
待审核 --管理员同意并填写退货地址--> 待用户退货
待审核 --管理员拒绝--> 已拒绝
待审核 --用户撤销--> 已撤销
待用户退货 --用户撤销--> 已撤销
待用户退货 --用户提交物流--> 待商家收货
待商家收货 --管理员确认收货--> 已退款
```

管理员拒绝必须填写 1-255 个字符的原因。退货退款同意时必须填写 1-255 个字符的退货地址或退货说明。用户提交物流时，物流公司和运单号均必填，长度分别不超过 64 个字符。提交物流后不能撤销。

状态不匹配的重复操作统一返回 `409`，不会重复执行副作用。

## 8. HTTP 接口

全部接口只使用固定路径 GET/POST。Token 继续只通过 `Authorization: Bearer ...` 请求头传递。

### 8.1 商城订单接口

| 方法与路径 | 请求 | 结果 |
| --- | --- | --- |
| `POST /api/orders/pay` | JSON `{ orderId }` | 模拟支付并返回订单详情 |
| `POST /api/orders/cancel` | JSON `{ orderId }` | 取消订单并返回订单详情 |
| `POST /api/orders/confirm-receipt` | JSON `{ orderId }` | 确认收货并返回订单详情 |

订单列表和详情响应增加支付、物流、完成时间、商品行 ID、商品行实付金额、已退款数量、已退款金额、可售后数量和当前售后摘要；保留原有字段，保证旧页面字段兼容。

### 8.2 内管订单接口

| 方法与路径 | 请求 | 结果 |
| --- | --- | --- |
| `POST /admin/api/orders/ship` | JSON `{ orderId, shippingCompany, trackingNo }` | 发货并返回订单详情 |

原有订单分页接口支持全部订单状态，详情增加物流、履约时间以及各商品行待履约数量。

### 8.3 商城售后接口

| 方法与路径 | 请求 | 结果 |
| --- | --- | --- |
| `POST /api/after-sales/apply` | JSON `{ orderItemId, type, quantity, reasonCode, description }` | 创建售后单 |
| `GET /api/after-sales` | 可选查询参数 `status` | 当前用户售后列表 |
| `GET /api/after-sales/detail` | 查询参数 `afterSaleId` | 当前用户售后详情 |
| `POST /api/after-sales/cancel` | JSON `{ afterSaleId }` | 撤销售后 |
| `POST /api/after-sales/return-shipment` | JSON `{ afterSaleId, shippingCompany, trackingNo }` | 提交退货物流 |

### 8.4 内管售后接口

| 方法与路径 | 请求 | 结果 |
| --- | --- | --- |
| `GET /admin/api/after-sales` | `afterSaleNo`、`orderNo`、`userId`、`type`、`status`、`page`、`size` | 分页列表，`size` 最大 100 |
| `GET /admin/api/after-sales/detail` | 查询参数 `afterSaleId` | 售后、订单、商品和日志详情 |
| `POST /admin/api/after-sales/approve` | JSON `{ afterSaleId, reviewRemark, returnAddress }` | 同意；仅退货退款要求退货地址 |
| `POST /admin/api/after-sales/reject` | JSON `{ afterSaleId, rejectReason }` | 拒绝 |
| `POST /admin/api/after-sales/confirm-receipt` | JSON `{ afterSaleId, reviewRemark }` | 确认收到退货、退款并恢复库存 |

所有接口继续使用 `ApiResponse<T>`；管理列表使用 `ApiResponse<PageResponse<T>>`。

## 9. 错误处理

在 `ErrorCode` 中增加：

- `ORDER_STATUS_INVALID`：订单当前状态不允许该操作。
- `ORDER_NOT_REFUNDABLE`：订单或商品不具备售后资格。
- `AFTER_SALE_NOT_FOUND`：售后单不存在或不属于当前用户。
- `AFTER_SALE_NOT_ALLOWED`：该类型不适用于当前订单状态。
- `AFTER_SALE_WINDOW_EXPIRED`：已超过 7 天申请期限。
- `AFTER_SALE_QUANTITY_EXCEEDED`：申请数量超过剩余可售后数量。
- `AFTER_SALE_ACTIVE_EXISTS`：该商品已有进行中的售后单。
- `AFTER_SALE_STATUS_INVALID`：售后单状态不允许该操作。
- `AFTER_SALE_RETURN_INFO_REQUIRED`：缺少退货地址或退货物流。

参数格式、枚举值、空文本和长度错误返回 `400`；资源不存在返回 `404`；状态、数量、并发和重复操作冲突返回 `409`；认证授权继续返回 `401/403`。

数据库唯一键或乐观状态更新产生的并发冲突转为稳定业务错误，不向调用方暴露 SQL 异常。

## 10. 商城小程序设计

`mallPage` 保持 Vant Weapp、TypeScript 和现有绿色水果商城视觉体系：

- “我的”页面展示真实待付款、待收货数量，并增加“售后服务”入口。
- 订单列表增加状态筛选以及支付、取消、查看详情、确认收货操作。
- 新增订单详情页，展示履约时间线、物流、金额、优惠、商品行退款情况和售后入口。
- 新增售后申请页，展示商品快照、可申请数量、类型、原因、说明和预计退款金额。
- 新增售后列表与详情页，展示状态时间线、审核意见、退货地址、退货物流；根据状态展示撤销或填写物流操作。
- 按钮提交期间禁用，接口错误提供明确提示；登录失效沿用现有统一处理。
- 固定页面路由通过查询参数传递订单或售后 ID，不生成动态路径。

## 11. 内管前端设计

`mallManagePage` 保持 Vue 3、TypeScript、Element Plus 和现有后台视觉体系：

- 订单页支持全部订单状态筛选，详情展示履约时间线、物流和商品待履约数量。
- 待发货订单提供发货对话框，物流公司与运单号必填。
- 侧边栏新增“售后管理”，并新增固定路由 `/after-sales`。
- 售后列表支持售后单号、订单号、用户 ID、类型和状态组合筛选与分页。
- 售后详情抽屉展示申请信息、商品与金额快照、审核状态、退货物流和完整操作记录。
- 待审核状态提供同意、拒绝操作；退货退款同意时要求退货地址，拒绝时要求原因。
- 待商家收货状态提供二次确认的“确认收货并退款”，明确提示库存恢复数量。
- 页面覆盖加载、空数据、请求失败、重复提交保护和窄屏适配。

## 12. 测试策略

所有生产行为遵循测试先行的红-绿-重构流程。

后端测试至少覆盖：

- 待支付订单支付、取消、恢复库存和退回优惠券。
- 待支付取消和各类退款正确减少 SKU 净销量，且重复请求不会把销量减为负数。
- 管理员发货、用户确认收货及所有非法状态跳转。
- 两种售后类型的资格判断。
- 待发货仅退款、待收货/已完成两种类型以及完成后 7 天边界。
- 商品行部分数量、多次申请、进行中单据互斥和超量拒绝。
- 优惠分摊、分币处理、商品行退款上限和订单退款上限。
- 用户撤销、管理员同意/拒绝、退货物流、确认收货。
- 待发货仅退款恢复库存并减少销量、发货后仅退款只减少销量、退货退款确认收货恢复库存并减少销量。
- 并发或重复请求不会重复退款、恢复库存或写入终态。
- 商城/管理员 Token 隔离、参数校验、统一错误响应。
- 两端路由架构继续只允许 GET/POST 且无路径变量。

前端验证至少覆盖：

- `mallManagePage` Vitest：订单发货、筛选、售后列表、审核、拒绝、退货确认和错误状态。
- `mallManagePage` 类型检查、ESLint 和生产构建。
- `mallPage` TypeScript 类型检查和 ESLint，即 `npm run check`。
- 页面手工验证加载、空状态、错误提示、状态按钮和重复提交保护。

最终验证：

- 根项目 Maven 全量测试和打包在 JDK 11 下通过。
- 本机 MySQL 8 成功执行并校验 Flyway V1-V12。
- Redis 6.2.13 认证连接正常。
- 商城端 8080 与内管端 8081 同时启动。
- 使用真实接口走通“下单 → 支付 → 发货 → 收货 → 申请退货退款 → 审核 → 提交物流 → 确认收货退款”的完整流程。
- 额外验证待发货仅退款和库存恢复，以及 PUT、DELETE、PATCH、HEAD、OPTIONS 继续返回 405。
